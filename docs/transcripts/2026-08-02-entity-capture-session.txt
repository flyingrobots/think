  What holds up

  The central claim is sound, and I verified the mechanism rather than taking it
  on faith. PatchBuilder._lowerNodePropertyIntent (PatchBuilder.ts:387-392)
  does _observedOperands.add(nodeId) unconditionally — there is no same-patch
  exemption — so legacy addNode+setProperty really does record reads {subject},
  while addEntity (PatchBuilder.ts:156-164) pushes its NodePropSet ops straight
  into _ops and bypasses that path entirely. The two sequences are
  operation-identical and footprint-distinct. The gate discriminates exactly
  what the commit says it discriminates.

  Three smaller things I checked because they were the plausible ways this could
  be quietly wrong:

  - patch.reads ?? [] is load-bearing, not defensive noise. Patch's _nonEmpty
  (Patch.ts:39-44) normalises empty arrays to undefined, so a real entity
  capture persists with reads === undefined — asserted at
  Runtime.entityCapture.integration.test.ts:46. This retracts the concern I
  raised before reading it: there is no "unrecorded" footprint state distinct
  from empty, so nothing is being laundered by the coalesce.
  - Round-trip is key-stable. LegacyNodePropertyKey.toString() returns its input
  verbatim, so propertyKey() performs no transformation and hydrate→re-lower
  reproduces keys. Both ends sort on the same key. No drift.
  - The atomicity claim is real. All validation in planEntityCapturePayload
  completes and returns ops before addEntity calls addNode, so a rejection
  leaves _ops untouched (PatchBuilder.entity.test.ts:51).

  Findings

  F1 — the guard is not merely weak on the lane path, it is unreachable, and 
  nothing says so. Measured, not reasoned: same runtime, same lane, same id
  written twice in a row → no error, cone becomes 2 patches. Runtime exposes
  only lane/fork/strand/settle/close (src/application/Runtime.ts) and Lane
  exposes only write (Lane.ts:100), so there is no public way to give a lane
  writer a materialized basis — scope.state is always null there. The
  scope.added arm can't fire either, since Lane.write is one intent per patch
  and planEntityCapturePayload runs before addNode. So E_PATCH_ENTITY_EXISTS is
  dead on the Runtime→Lane path.

  The CHANGELOG's "A writer that has not materialized has no basis to check" is
  grammatically conditional and implies a lane writer might. It cannot. The
  accurate statement is that the guard is reachable only for direct PatchBuilder
  users opened against a materialized state. This matters downstream: it makes
  Think's Phase 1B sortKey tiebreaker the sole defense, with no substrate
  backstop on the production path at all.

  F2 — the test named "under concurrent writers" contains no concurrency.
  capture() opens a Runtime, writes, and closes; writer-b opens only after
  writer-a has closed. So case 1 ("two writers from the same frontier") passes
  for the same reason as case 2 (no materialized basis). The doc comment at the
  top presents these as two distinct mechanisms; the test isolates one. The
  claim is nonetheless true — I held both runtimes open before either wrote, and
  b was admitted with patchCount 2 — so the repair is to make the test do that,
  not to retract anything. Worth naming: this is exactly the "a fix added a
  variable that confounds what the test isolates" pattern flagged in the last
  session's own self-assessment.

  F3 (minor) — two assertions can't fail for the reason they're named. The
  integration test's MEMORY literal is already in lexicographic key order, so it
  cannot detect a lost sort (the canonical-order unit tests do cover it, so
  coverage exists — the integration assertion is decorative). And the
  five-capture cone test writes identical {...MEMORY} to all five subjects, so
  cross-attributed slices would still pass; distinct payloads would make it a
  real check.

  F4 (minor, doc precision) — "reads empty, writes exactly the new id" is a 
  property of a patch containing only the capture, not of the method. Nothing
  stops addEdge(...).addEntity(...) in one patch on the advanced surface; that
  patch gets a wider footprint and then fails hydration. It fails closed, which
  is correct — but the PatchBuilderEntity docstring reads as unconditional.
  Unreachable via the Intent/Lane API.

  Not re-run: the full 7,336-test suite, lint gates, semgrep, typecheck. The
  handoff records them green and the tree is byte-identical to that state.

  Verdict: the commit does what it claims. Two of its three retractions are
  fully evidenced. The third — uniqueness — is under-evidenced in the direction
  of not being pessimistic enough, which is the good direction to be wrong in
  but still worth correcting before it becomes the documented contract Think
  builds on.
